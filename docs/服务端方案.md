# 拉了么 · 服务端方案

**版本** 草案 v0.1　**日期** 2026-11-18　**状态** 待决策

---

## 一、结论先行

**推荐路线：微信云开发（CloudBase），基础套餐 19.9 元/月。**

理由有三条，按权重排序：

1. **省掉两件最麻烦的事**：不用买域名、不用备案；不用自己维护 access_token，云调用直接发订阅消息。对个人项目来说，这两件事吃掉的时间往往超过写业务代码。
2. **天然拿到 openid**：小程序端 `wx.cloud.callFunction` 自带用户身份，不需要自己实现登录态、session、签名校验。
3. **成本可控**：基础套餐 20 万次调用/月、2GB 容量，按目前的产品量级（每天几次读写/人）可支撑数千活跃用户。超出按量计费，单价很低。

不推荐一开始就上轻量服务器：固定成本更高（还要算备案与运维时间），且这个产品的服务端逻辑很轻，用不到一台完整的机器。

## 二、必须先做的一个决定：隐私口径

产品现在的承诺是「数据只在本机，从未离开你的手机」。加了服务端，这句话就不成立了。有三条路可选：

| 方案 | 口径 | 优点 | 代价 |
|---|---|---|---|
| **A. 默认不上传，用户手动开启云同步** | 「默认只存本机；开启后加密上传，用于换机与好友功能」 | 守住原有承诺，老用户无感 | 好友/排行/推送都依赖开启，转化率取决于引导 |
| **B. 首次授权即上传（弹窗说明）** | 「授权后数据同步到云端，用于多人功能」 | 功能覆盖最全 | 与现有文案冲突，必须全站改口径 |
| **C. 双模式并存：本地版 / 云版** | 两个入口 | 最彻底 | 维护成本翻倍，不推荐 |

**建议选 A**，理由：这个产品的核心资产是「信任」。一旦默认上传，之前所有关于隐私的表述（README、隐私指引、致谢）都要重写，而且会让老用户觉得被背叛。改为「可选开启」既保住了承诺，也给了需要的人一个开关。

对应的产品改动：

- 「我的」页新增「云同步」开关，默认关闭
- 首次开启时弹窗说明：上传什么、发给谁看、如何删除
- 数据页新增「删除云端数据」（与本地清空分开）
- 全站文案从「从未离开你的手机」改为「默认只存本机，开启云同步后加密上传」

## 三、四个功能的服务端设计

### 3.1 换机与清缓存后恢复数据

**目标**：清理小程序缓存、换手机、重装，只要用同一个微信登录，就能把历史全部拉回来。

**数据**：`records` 表按 `(openid, client_id)` 唯一。`client_id` 由端上生成（时间戳 + 随机），保证同一条记录重复上传不会产生副本。

**同步策略：本地优先（local-first）**

- 写：本地先落盘、界面立即反馈，随后异步批量推送云端；失败进入重试队列，下次启动补传
- 读：启动时拉「拉取游标之后」的增量（服务端返回 `serverCursor`），合并进本地
- 冲突：同 `client_id` 以 `updatedAt` 较新者为准（LWW）；删除用软删 `deletedAt`，避免删了又被旧数据推回来

**恢复流程**：新设备登录 → 拉全量（分页 200 条/次）→ 写入本地 → 本地显示与旧设备一致。

**边界**：
- 服务端只做「搬运」，不做唯一数据源——本地仍是主存储，离线可用这一点不能丢
- 拉全量时以服务端为准覆盖本地同 `client_id` 的记录，但保留本地独有的（未上传成功的）

### 3.2 每日打卡提醒

**目标**：当天没有记录时，晚上提醒一次。

**微信的硬约束**（这一条决定功能形态，必须先讲清）：

个人主体小程序**只能使用一次性订阅消息**。规则是：用户每点一次「允许」，你就获得**一条**下发额度（按「用户 + 模板」计，7 天内有效）。没有额度就发不出去，任何人都绕不过。

长期订阅消息只对政务民生、医疗、交通、金融、教育等类目开放，个人主体申请不到。

**因此「每天提醒」的真实形态是**：用户每次在小程序里完成记录或打开首页时，请求一次订阅授权；授权累积成额度；服务端每天 20:00 检查，若「当天无记录」且「额度 ≥ 1」则发一条，发完扣额度。

这意味着：**用户几天不打开，额度耗尽后就收不到提醒**。这不算缺陷——只提醒还在用的人，本身是合理的克制。

**实现**：
- 端上在「记录成功」后调用 `wx.requestSubscribeMessage({tmplIds:[每日提醒模板]})`
- 授权结果上报服务端：`POST /push/quota`，服务端按 `(openid, templateId)` 累加
- 定时触发器（云函数定时触发，每天 20:00）：查当天无记录且有额度的用户，调用 `subscribeMessage.send`，成功后扣额度并写 `push_logs`

**防止打扰**：同一天同一用户最多一条；用户关闭开关后不再请求授权。

### 3.3 好友排名与好友情况

**关系模型**：`friendships` 表，`requester` / `addressee` / `status(pending|active|blocked)` / `createdAt`，双向只存一条。

**可见范围**（这是本功能的核心设计，不能含糊）：

| 字段 | 好友可见 | 说明 |
|---|---|---|
| 今日是否已记录 | 是 | 只有「拉了 / 还没」 |
| 连续天数 | 是 | |
| 段位 | 是 | |
| 近 7 天次数 | 是 | 聚合值 |
| 平均时长 | 是 | 聚合值 |
| 单条记录的形状/颜色/感受 | **否** | 永不下发 |
| 记录时间点 | **否** | 只给「今天有没有」 |

**排名口径**：按「近 7 天记录天数 → 连续天数 → 平均质量分」三级排序，同分并列。不做「谁拉得多」这种鼓励刷量的排名。

**好友邀请**：分享卡片带 `inviteToken`（一次性、48 小时有效），对方点击后进入授权页 → 建立关系 → 双方各收到一条「已成为好友」的服务通知（可选）。

### 3.4 好友打卡提醒

**目标**：好友完成记录时，通知其他好友，每天最多一条。

**流程**：好友 A 的记录写入成功 → 服务端查 A 的所有 active 好友 → 对每个好友 B：若今天还没给 B 发过此类提醒 → 发一条「你的好友完成今日打卡」→ 写 `push_logs`。

**「每天仅一次」的两个维度**（容易混淆，必须都做）：
- 对接收者 B：每天最多收到一条「好友打卡」类提醒（不论几个好友打卡）
- 对触发者 A：一天只触发一次（A 当天第一条记录才触发，第二条静默）

**同样受一次性订阅约束**：B 必须有该模板的可用额度。所以端上要在合适时机（比如查看好友页时）请求第二个模板的授权。

**隐私红线**：提醒里不出现好友的具体记录内容，只有「已完成今日打卡」这一句。

## 四、数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | `_id`(openid) / `nick` / `avatar` / `createdAt` / `lastActiveAt` / `settings` | 昵称头像需用户主动填写（微信已不允许静默获取） |
| `records` | `_id` / `openid` / `clientId` / `ts` / `durationMin` / `bristol` / `mood` / `color` / `updatedAt` / `deletedAt` | 唯一索引 `(openid, clientId)` |
| `friendships` | `_id` / `a` / `b` / `status` / `createdAt` | 双向一条，`a < b` 字典序 |
| `invites` | `_id` / `token` / `from` / `expireAt` / `used` | 一次性、48 小时 |
| `push_quota` | `_id` / `openid` / `templateId` / `count` / `updatedAt` | 按「用户 + 模板」记额度 |
| `push_logs` | `_id` / `openid` / `type` / `date` / `sentAt` | 用于「每天仅一次」判重 |
| `devices` | `_id` / `openid` / `clientId` / `lastSyncAt` | 多端同步游标 |

索引建议：`records(openid, ts desc)`、`records(openid, clientId)` 唯一、`push_logs(openid, type, date)` 唯一。

## 五、接口清单（云函数）

| 函数 | 作用 | 关键返回 |
|---|---|---|
| `user.login` | 首次登录建档、更新 `lastActiveAt` | `profile` |
| `sync.pull` | 按游标拉增量（含软删） | `records[]` + `nextCursor` |
| `sync.push` | 批量 upsert（≤200 条/次，幂等） | `accepted[]`、`conflicts[]` |
| `friend.invite` | 生成邀请 token | `token`、分享参数 |
| `friend.accept` | 接受邀请，建立关系 | `ok` |
| `friend.list` | 好友列表 + 今日状态 + 段位 | `friends[]` |
| `friend.rank` | 近 7 天排名 | `rank[]` |
| `push.report` | 上报订阅授权，累加额度 | `quota` |
| `push.settings` | 开关每日提醒 / 好友提醒 | `settings` |
| `cron.daily` | 定时触发：每日提醒 + 额度清理 | 统计 |
| `record.onCreated` | 记录写入后触发好友通知（可并入 `sync.push`） | — |

云函数环境变量：`APPID` / `APPSECRET`（云调用可免，若用 HTTP 调则需）。

## 六、订阅消息的现实约束（重点）

这一节单独列，因为它是本次需求里唯一「产品诉求与平台规则冲突」的地方。

| 项目 | 规则 | 对产品的影响 |
|---|---|---|
| 可用类型 | 个人主体仅一次性订阅 | 无法实现「永久每天推」 |
| 额度计量 | 按 `(用户, 模板)` 计，授权一次 = 一条 | 需在端上设计授权触点，累积额度 |
| 有效期 | 7 天 | 长期不登录的用户额度会失效 |
| 触发条件 | 必须由用户交互触发，禁止启动即弹 | 只能在「记录完成」「进好友页」等时机请求 |
| 内容限制 | 只能用模板关键词，不得含营销内容 | 文案自由度低，需提前申请合适模板 |

**可行的额度策略**（合规做法，不是绕过）：

1. 记录成功后请求一次（用户此刻正有正反馈，通过率最高）
2. 打开小程序时若额度 < 3，再请求一次
3. 端上显示「剩余提醒次数 N」，把额度变成可见的东西

## 七、采购对比

| 方案 | 月成本 | 免备案 | 运维 | 适合度 |
|---|---|---|---|---|
| **微信云开发（推荐）** | 19.9 元（基础套餐：20 万调用 / 2GB / 2GB 出流量） | 是 | 无 | ★★★★★ |
| 腾讯云云托管 CloudRun | 约 30–100 元（容器按量 + 最小实例） | 仍需域名 | 低 | ★★★ |
| 轻量应用服务器 Lighthouse | 约 50–90 元（2C2G）+ 域名 | 否，需备案 | 中（自己装库、备份、证书） | ★★ |
| 纯 Serverless（SCF + 云数据库） | 按量，通常 < 10 元 | 是 | 低 | ★★★ |

> 云开发的免费体验环境有个坑：**小程序发布上线后，环境到期时间变为上线后第 15 天**，之后必须转付费，否则停服。所以要按 19.9 元/月 做预算，不要按免费做。

**成本测算（按 1000 活跃用户估算）**：
- 每人每天 2–3 次记录写入 + 1 次拉取 ≈ 4000 次调用/天 ≈ 12 万次/月，接近基础套餐 20 万次上限
- 容量：1000 人 × 3 年 × 每天 2 条 ≈ 200 万条记录，约 400MB，2GB 容量够用
- 结论：**1000 人以内基础套餐足够；超过 2000 人再考虑标准版或按量**

## 八、实施分期

| 阶段 | 内容 | 依赖 |
|---|---|---|
| M1 | 云环境 + 登录 + 记录同步（含换机恢复） | 隐私口径确定 |
| M2 | 订阅消息：每日提醒（含额度体系） | 后台申请模板 |
| M3 | 好友关系 + 排名 + 好友情况 | M1 |
| M4 | 好友打卡提醒（每天一次） | M2 + M3 |

每阶段的验收标准：

- M1：清缓存后重进，记录条数与内容与清空之前一致
- M2：有额度时能收到提醒，无额度时静默跳过，不重复发
- M3：好友能看到彼此的聚合数据，看不到单条明细
- M4：三个好友同时打卡，接收者只收到一条

## 九、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 订阅消息模板审核不通过 | 提醒功能无法上线 | 提前在后台用公共模板库选型，不用自定义模板 |
| 额度耗尽导致「提醒不灵」 | 用户投诉 | 端上显示剩余额度；文案说明「只提醒还在用的人」 |
| 同步冲突造成重复记录 | 数据脏 | `clientId` 唯一索引 + 幂等 upsert |
| 好友功能引发隐私争议 | 信任受损 | 只开放聚合字段；关系需双向确认；可随时解除 |
| 云开发免费额度到期 | 服务中断 | 上线即转付费，写进运维清单 |
